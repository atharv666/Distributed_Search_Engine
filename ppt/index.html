01 · CONTEXT

What is a search engine?

A search engine turns a collection of pages into a fast, ranked answer for a user’s query.

Google Search · Microsoft Bing · DuckDuckGo

  • Collects public web pages.
  • Extracts useful text into logical documents.
  • Builds an inverted index for fast lookup.
  • Ranks matching documents by relevance.
Raw HTML → Parser → Documents → Tokenizer → Inverted index → Ranked results

02 · MOTIVATION

Why does search become distributed?

One central server
all documents · all postings · every query⚠

A single server eventually reaches storage, throughput, and availability limits.

  • Storage: complete indexes can outgrow memory.
  • Throughput: concurrent users compete for one processor.
  • Availability: one failure stops all search.
  • Growth: adding nodes is easier than replacing one server.

05 · INDEXING

Tokenization and inverted index

We avoid scanning every page for every query by mapping each term to documents that contain it.

Text: “Python data structures include lists.”
Tokens: [python, data, structures, include, lists]

Term → posting list

data → D1: tf 3, positions [10,42] · D19: tf 7, positions [1,18]

structures → D1: tf 2 · D19: tf 5

Each posting stores document ID, term frequency, and positions.

06 · RANKING

TF‑IDF and cosine similarity

TF(term, doc) = occurrences / total tokens
IDF(term) = log(Nglobal / dfglobal)
TF‑IDF = TF × IDF

TF rewards important terms within a document; IDF reduces the impact of very common terms.

Example

N = 30; structures occurs in df = 5.

IDF = log(30 / 5) = 1.79

D19 has 5 occurrences in 250 tokens:

TF = 0.02 · TF‑IDF = 0.0358

The query and candidate documents become sparse TF‑IDF vectors. Cosine similarity measures how closely they align.

03A · CENTRALIZED LIMITS

Why a singleton architecture is not enough

Centralized search

One machine
crawler + document store + index + ranking

Every query competes for the same CPU, memory and index. A failure makes the service unavailable.

  • One large index to load and maintain
  • Sequential bottleneck under many queries
  • Single point of failure

Our distributed search

Node 1Node 2Node 3

Documents and postings are partitioned. Nodes search in parallel and the coordinator merges the best candidates.

  • Horizontal data and query scaling
  • Independent processes over RPC
  • Partial results when one node fails

Why not distribute crawling first? For a controlled academic corpus, centralized crawling is simpler and safer. Distribution is demonstrated in the search-serving path, where partitioned indexes and parallel query processing create real distributed-system requirements.

It is deterministic, easy to inspect in a demonstration, and ensures every document belongs to exactly one node.

Invariant

07A · INVERTED INDEX

Worked retrieval example

Three tiny documents

D1: "python data structures"
D2: "python modules"
D3: "distributed data storage"

Query: python data

The query tokenizer produces [python, data].

Posting-list lookup

python → [D1, D2]
data → [D1, D3]

Union candidates: D1, D2, D3

Strict AND intersection: D1 only

Our ranked retrieval uses the union, so a document that matches part of a natural-language query can still be useful.

Why positions? They support snippets now and can later support phrase queries such as "data structures" and proximity ranking.

08A · COSINE RANKING

How cosine similarity chooses the order

Query vector

Q = [python: 0.5, data: 0.5]

Each query-term weight uses query TF multiplied by global IDF.

Document vector

D1 = [python: 0.6, data: 0.4]

Each document-term weight uses local document TF multiplied by the same global IDF.

cos(Q, D1)
(Q · D1) / (|Q| × |D1|)
Higher = more similar

Why shared global IDF matters

If Node 1 used its own IDF and Node 2 used another, scores would have different scales and could not be ranked fairly.

Our solution

Local TF stays local; a build step combines global document frequencies and produces one shared global_statistics.json for every node.

09A · TOP‑K CORRECTNESS

Why each node can return only local Top‑K

Example: global Top‑10 requested

Node 1 scores: 0.99, 0.98, … 0.90
Node 2 scores: 0.88, 0.75, …
Node 3 scores: 0.67, 0.51, …

The coordinator receives Top‑20 from each node, merges them, then selects the final Top‑10. Node 1 can legitimately contribute all final results.

Key argument

If a document is not in its shard’s local Top‑20, then at least 20 documents in that same shard score above it.

Therefore it cannot be in a global Top‑10.

Condition: all nodes use the same global scoring formula and local K ≥ final K.

10A · FA–1 DESIGN ISSUES

Design decisions and trade-offs

Design questionDecision in this projectReason
How is data divided?Document-based range shardsSimple, deterministic and easy to demonstrate.
Where is the index?One local inverted index per nodePrevents the coordinator becoming a storage bottleneck.
How are scores comparable?Global df/IDF, local TFAllows safe global merge of local rankings.
How do processes communicate?gRPC + Protocol BuffersTyped RPC contract and actual network communication.
What if a node fails?Timeout + partial resultsThe search service remains available in degraded mode.
